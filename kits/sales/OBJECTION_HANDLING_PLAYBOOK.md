# Objection Handling Playbook

**Last Updated:** 2025-01-20  
**Status:** Revenue Bootstrap - Active  
**Purpose:** Quick reference for handling common objections during sales

## Overview

This playbook provides quick responses to common objections. Each objection includes:
- **The objection:** What they're saying
- **The concern:** What they're really worried about
- **The response:** What to say
- **Next steps:** How to move forward

**Philosophy:** Don't argue, understand and address.

---

## Common Objections

### Objection: "We don't have API access"
**Concern:** Can't integrate, technical barrier

**Response:**
"Settler requires API access to your systems (Stripe, Shopify, QuickBooks, etc.). If you don't have API access, we can help you set it up—it's usually straightforward. If API access isn't possible, you might be better served by manual reconciliation tools. I'd be happy to reconnect when you have API access."

**Next Steps:**
- Offer to help set up API access
- Provide API setup guide
- Reconnect when API access available

---

### Objection: "We're too small"
**Concern:** Not enough volume, not worth it

**Response:**
"Settler is designed for companies doing 10K+ transactions/month. If you're smaller, manual reconciliation may be sufficient. However, if you're growing and expect to reach 10K+ transactions soon, it might make sense to start now. I'd be happy to reconnect when you're processing more volume."

**Next Steps:**
- Confirm volume (how many transactions/month?)
- If growing, offer pilot to test
- If too small, reconnect later

---

### Objection: "We already have a process"
**Concern:** Current process works, no need to change

**Response:**
"If your current process works, great. Settler is for companies where reconciliation takes 2+ days/month and is error-prone. If that's not you, we may not be the right fit. However, if you're spending significant time on reconciliation or experiencing errors, it might be worth exploring. Would you like to try a 14-day pilot to see if Settler can help?"

**Next Steps:**
- Understand current process (time, errors)
- If pain exists, offer pilot
- If no pain, disqualify politely

---

### Objection: "We need custom features"
**Concern:** Standard features not sufficient, need customization

**Response:**
"Settler is a SaaS platform with standard integrations (Stripe, Shopify, QuickBooks, PayPal, Xero). If you need extensive custom development or on-premise deployment, we're not the right fit. However, if standard integrations meet your needs, Settler might work. What specific custom features do you need?"

**Next Steps:**
- Understand custom requirements
- If standard features sufficient, offer pilot
- If extensive customization needed, disqualify politely

---

### Objection: "We need compliance certifications"
**Concern:** Need HIPAA, FedRAMP, or other certifications

**Response:**
"Settler is designed for e-commerce and SaaS companies. If you need HIPAA, FedRAMP, or other industry-specific certifications, we may not be the right fit. However, we can discuss Enterprise options if you're interested. What specific compliance requirements do you have?"

**Next Steps:**
- Understand compliance requirements
- If standard compliance sufficient, offer pilot
- If industry-specific certifications needed, disqualify politely

---

### Objection: "We don't have budget"
**Concern:** No budget, can't afford

**Response:**
"Settler starts at $99/month (Starter plan). If you don't have budget, we may not be the right fit right now. However, if reconciliation takes 2+ days/month, Settler typically saves $2K-$5K/month in labor costs—so ROI is usually clear. I'd be happy to reconnect when budget is available."

**Next Steps:**
- Understand budget situation (no budget vs pending approval)
- If pending approval, offer pilot to demonstrate ROI
- If no budget, reconnect later

---

### Objection: "We need to think about it"
**Concern:** Not ready to decide, need more time

**Response:**
"Of course. What specifically would you like to think about? Is there something I can clarify or provide more information about? I'd be happy to answer any questions or provide additional resources."

**Next Steps:**
- Understand specific concerns
- Address concerns with information
- Set follow-up date (don't let it drift)

---

### Objection: "We need to talk to our team"
**Concern:** Need stakeholder buy-in, decision committee

**Response:**
"Absolutely. Who else needs to be involved in the decision? I'd be happy to include them in a demo or provide information they need. What information would be helpful for them?"

**Next Steps:**
- Identify stakeholders
- Offer to include in demo or provide information
- Set follow-up date with stakeholders

---

### Objection: "We're evaluating other options"
**Concern:** Comparing alternatives, not ready to commit

**Response:**
"That makes sense. What other options are you evaluating? I'd be happy to help you compare Settler to other solutions. What criteria are you using to evaluate?"

**Next Steps:**
- Understand alternatives being evaluated
- Provide comparison information
- Offer pilot to test Settler

---

### Objection: "We're not ready yet"
**Concern:** Not the right time, other priorities

**Response:**
"I understand. What would need to change for you to be ready? Is there a specific timeline or event that would make this a priority?"

**Next Steps:**
- Understand what would make them ready
- Set reconnect date
- Stay in touch with value-add content

## Objection Handling Framework

### Step 1: Acknowledge
**Don't:** Argue or dismiss
**Do:** Acknowledge their concern: "I understand that's a concern."

### Step 2: Understand
**Don't:** Assume you know their concern
**Do:** Ask clarifying questions: "Can you tell me more about that?"

### Step 3: Address
**Don't:** Give generic responses
**Do:** Provide specific information or alternatives

### Step 4: Move Forward
**Don't:** Let objection end conversation
**Do:** Convert to next step: "Would you like to try a pilot?"

## Objection Prevention

### Best Practices
- **Qualify early:** Disqualify bad fits before objections arise
- **Set expectations:** Be clear about what's included/excluded
- **Provide information:** Share pricing, features, requirements upfront
- **Address concerns:** Proactively address common concerns

### Common Prevention Strategies
- **Pricing transparency:** Share pricing upfront (no surprises)
- **Scope clarity:** Be clear about what's included/excluded
- **Requirements clarity:** Be clear about API access, technical requirements
- **ROI clarity:** Show ROI upfront (time savings, cost savings)
