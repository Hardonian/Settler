# Header / CSP Verification Contract

Last updated: 2026-03-08

## Contract classes

The header probe now separates checks into explicit classes:

- **enforced** (blocking)
  - API routes with concrete `GET`/`HEAD` handlers under middleware scope
  - denial probe (`/api/v1/runs` expecting 401/403 + no-store)
- **best-effort** (non-blocking)
  - webhook/cron API routes that are runtime-constrained
- **framework-limited** (non-blocking)
  - dynamic routes not directly probeable without parameters
  - synthetic method-not-allowed paths (405 generated by framework)
  - framework fallback probes (`/admin` redirect, unknown 404)

## Enforced headers

- HTML enforced: `content-security-policy`, `strict-transport-security`, `x-content-type-options`, `x-frame-options`, `referrer-policy`, `permissions-policy`
- API enforced: `strict-transport-security`, `x-content-type-options`, `x-frame-options`, `referrer-policy`, `permissions-policy`
- Observability-only (non-blocking): `x-request-id`

For denial responses (`401`/`403`), `cache-control` must include `no-store`.

## Output model

`artifacts/security/header-probe-latest.json` and run artifact now include per-check:

- route class and contract type
- expectation class
- required headers
- observed headers and status code
- machine-readable mismatches
- blocking vs non-blocking failure semantics

This keeps hard failures focused on enforceable guarantees and prevents framework-noise from appearing as launch-blocking evidence.
